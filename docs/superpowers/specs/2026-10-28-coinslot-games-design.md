# Coin Slot 第二批游戏设计（Plan 2）

日期：2026-10-28 · 作者：@0xasten · 状态：待作者审阅

本文是 `2026-10-28-coinslot-design.md`（下称「主文档」）的续篇，只写 Plan 2 新定下来的事。主文档里已定的约束、Claude 联动（§6）、画面与性能底线（§8）、开发流程（§12）照旧有效，这里不重复。

## 1. 要做什么，为什么

Plan 1 交付了共享联动模块和 reef-net。Plan 2 交付剩下五个游戏，并把 reef-net 改名，让六个游戏凑齐首发阵容。

作者试玩 reef-net 后认可它的整体路子，后面五个照它来：打开就能玩、第一屏没有说明文字、Claude 做完就弹横幅暂停、面板重新挂载时存档不丢。

**发布节奏**（作者原话归纳）：不设截止日期，但要尽快；做完、没有明显 bug 就发。

## 2. 名字（作者已定）

**原则：用户一看名字就知道是什么游戏。** 一眼可认比整套主题统一更重要，所以不用统一主题（海洋主题已被否决），名字直接说出玩法类型。唯一要绕开的是商标名（Breakout、Tetris、Flappy Bird 等），只用通用类型词。

| 类型 | 插件名 / 斜杠命令 |
| --- | --- |
| 捕鱼射击（原 reef-net） | `fish-shooter` |
| 打砖块 | `brick-breaker` |
| 贪吃蛇 | `snake` |
| 横版飞机射击 | `space-shooter` |
| 上下扑腾、穿过障碍 | `tap-flyer` |
| 横向奔跑、跳跃躲障碍 | `jump-runner` |

- 斜杠命令与插件名相同，例如 `/brick-breaker`。fish-shooter 的命令也随之从 `/reef` 改成 `/fish-shooter`。
- **发布前要查一遍撞名**（插件市场、npm、GitHub 上的同名 Claude Code 插件）。撞了就提替代名给作者拍板，不要自己改。
  - 撞名检查**不阻塞开发**（构建者的决定）：插件名只在本 marketplace 内唯一，安装命令带 `--marketplace beasaltfish/coinslot`，真正可能冲突的只有斜杠命令。所以先用这些名字开发，撞名检查放在 Plan 2 最后一步，需要改名时一次性改。
- 主角形象仍然原创，按各自游戏最顺手的来画，不限主题。跑酷类的主角不能是恐龙（与 claudedino 区分），扑腾类不能是小鸟加绿水管。

## 3. 改名：reef-net → fish-shooter

- 插件目录、manifest、marketplace 条目、atom 的 `plugin` 键、斜杠命令、面板标题全部改掉。
- 还没公开发布，所以**不做存档迁移**：atom 的 `plugin` 键直接改成 `fish-shooter`，快照结构不变，旧 `reef-net` 存档静默作废，这是接受的代价。
- **不保留 `/reef` 别名**：从没公开过，别名只会多一个要维护的命令。
- 改名放在 Plan 2 的第一步或者跟共享外壳抽取一起做，由构建者决定，但必须早于第一个新游戏的真机试玩，避免作者在两个名字下各装一遍。

## 4. 离开与暂停（所有新游戏）

动作游戏一秒没人操作角色就会死，所以 Plan 2 比 fish-shooter 更需要暂停。

- **开局停在「按任意键开始」**（或点击），不是一打开就跑。游戏名可以出现在这一屏，但除了这一句不放说明文字（主文档反目标：第一屏不堆说明）。
- **按 Esc 回对话框时立即暂停**；回来点击或按任意非 Esc 键继续。Esc 是唯一明确的「我要离开了」信号。
  - **待验证**：Esc 可能被 Claude Code 自己吃掉，传不到 `Client`。抽外壳时先用 fish-shooter 实测一次，结论写进 `docs/probe-findings.md`。
  - 如果传不到：退回空闲自动暂停（见下），并对所有快节奏游戏启用。
- **空闲自动暂停**：只给快节奏的三个——`tap-flyer`、`jump-runner`、`space-shooter`——约 3 秒没有任何按键或鼠标输入就暂停。`snake`、`brick-breaker`、`fish-shooter` 不加：贪吃蛇正常玩时本来就常常几秒不按键，加了只会打断人。
  - 具体秒数由构建者按手感调，3 秒是起点。
- 暂停画面统一用共享 overlay，和「CLAUDE IS DONE」横幅同一套样式，文案例如 `PAUSED · PRESS ANY KEY`。
- 「CLAUDE IS DONE」横幅（主文档 §6 第一层）对所有游戏照旧生效，不变。
- **暂停策略按游戏配置**（构建者的决定）：外壳提供「Esc 暂停」「空闲暂停（秒数）」两个开关，每个游戏自己声明，不写死在外壳里。
- **Esc 传不到时的退路**（构建者的决定）：三个快节奏游戏照上面 3 秒；`snake` 也加空闲暂停，但门槛放宽到约 6 秒——否则离开去打字时蛇必死，而正常玩时 6 秒不按键很少见。`brick-breaker` 和 `fish-shooter` 仍不加：球掉了只丢一条命、鱼不会伤人。
- **「输入」怎么算**（构建者的决定）：引擎实际送进 `Client` 的事件都算（按键、点击，鼠标移动若能送达也算）。先在 Esc 实测时一并记下哪些事件能送达，空闲计时按实测结果写。
- **重新挂载后一律恢复成暂停态**（构建者的决定），显示 `PRESS ANY KEY`。存档最多丢约 1 秒，快节奏游戏直接恢复运行可能让角色在玩家回来前就死掉。

## 5. 每个游戏的 Claude 联动第二层

照主文档 §6 第二层：每次 `tool.call` 在游戏里生成一个奖励物，**只给奖励，不加难度**。

| 游戏 | 奖励物 |
| --- | --- |
| brick-breaker | 落下一个道具（例如加宽挡板、多一颗球） |
| snake | 多一颗发光食物，吃了加分但不额外变长太多 |
| space-shooter | 飞来一个补给（火力升级或护盾） |
| tap-flyer | 障碍间多一枚金币 |
| jump-runner | 路上多一枚金币 |

具体道具效果由构建者定，原则是录屏里一眼看得出「Claude 越忙，游戏越热闹」，且不会让玩家因此死掉（例如不在障碍上生成金币）。

## 6. 开发顺序与节奏

1. **共享外壳**：把 reef-net 里每个游戏都会重复的部分抽进 `shared/`——主循环（固定步长 tick）、存档与恢复（快照经 `surface.post` 进 hooks 侧 atom、props 带回）、横幅与暂停 overlay、尺寸提示、`drawCells`（格子合并成 `Text` 段）、开局与 Esc/空闲暂停。再用它改写 fish-shooter，行为不变、测试照过。
   - 共享模块的具体 API 留给构建者（主文档 §12），但判据是：**第二个游戏（brick-breaker）只写自己的 `sim`、`render` 和少量胶水**。抽完就用 brick-breaker 来验证，发现外壳不够用就当场改外壳，不在游戏里绕开。
   - **Esc 实测排在外壳抽取的最前面**，结果决定暂停那部分怎么写（见 §4）。
   - **外壳改写后的 fish-shooter 不单独约作者试玩**（构建者的决定）：现有测试是这一步的验收线，作者在试玩 brick-breaker 时顺带玩一局 fish-shooter，两次合一次。
   - **帧率**（构建者的决定）：外壳带一个只在开发时打开的帧耗时读数；验收线是 90×13 inline 下作者肉眼看不出卡顿。撑不住时按主文档 §8 的顺序退：先减粒子，再降渲染分辨率。
2. brick-breaker
3. snake
4. space-shooter
5. tap-flyer

**每个游戏做完都由作者真机试玩一次，过了再开始下一个。** 理由：reef-net 的几个真 bug（焦点信号失效、弹窗重新挂载）都是真机才发现的，测试全绿拦不住；逐个试玩让同一个坑只踩一次。

- 没有截止日期，所以**不预先砍游戏**。某个游戏做到一半明显不好玩，停下来问作者，不硬做完。
- 每个游戏的 `sim` 和 `render` 保持纯函数、可在 Bun 里脱离 Claude Code 运行，并接受固定 seed——Plan 3 的展示页帧录制要用（主文档 §10）。

## 7. 完成标准

单个游戏：
- `bun run check` 全绿（`claude plugin validate`、`tsc`、`claude plugin test`、bundle 无漂移）。
- 测试覆盖 `sim` 的核心规则、暂停与恢复、重新挂载后存档恢复。
- 在 40×10 的最小面板与常见 inline 尺寸（约 90×13）下都能玩。
- 作者真机试玩没有发现明显 bug。

整个 Plan 2：六个游戏都满足上面这条，名字查过撞名，README 列出六个游戏与各自的一行安装命令。

## 8. 不在 Plan 2 里

- 展示页与帧录制（Plan 3）。
- 「全部安装」的形式（留给构建者，可放 Plan 3 一起做）。
- 推广素材、推文、录屏（发布前另起一轮）。
- 提示音（主文档已砍，Plan 2 不加回来，除非作者提出）。

## 9. 构建者的决定空间

- 共享外壳的具体 API 与文件划分。
- 各游戏的数值、关卡、手感、计分方式、失败后的重开方式。
- 各游戏的主角与配色（在原创与「一眼可认」两个前提下）。
- 空闲暂停的具体秒数。
- 测试的组织方式。
